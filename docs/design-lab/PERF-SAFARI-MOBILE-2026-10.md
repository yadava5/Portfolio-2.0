## 2. Phase 1 — desktop Safari, high-confidence, small diffs

**P1.1 Contour: short layer with wrapped travel, behind a dynamic guard (F2–F4, F14).** Height `calc(100vh + 620px)` (one pattern tile of extra travel), transform `translateY(-((y*0.07) % 620))`, parallax/opacity/night-invert unchanged. **[r2] Guard, decided in `cacheGeometry()` (≈:4500) and on every real resize:** the short moving layer only when **[r3] `navigator.maxTouchPoints <= 1`** (iPadOS Safari reports a Mac UA, so no sniffing; touch-screen Windows/Chromebooks also go static, which costs them only the 7% parallax of a 0.05 texture) **and** `vh + 620 ≤ 1900` (F14 brackets it: 1920 fine, 2120 slow, line at 2048) (margin under macOS's 2048; covers 1440p-tall windows and zoomed-out seats, since `innerHeight` is in CSS px); otherwise `contour-static` (no per-frame write; F3 shows static ≡ short on cost, it only loses the 7% parallax of a 0.05-opacity texture). The guard is one class on `#contour` plus one branch in the write at :8231. Wrap correctness: the period is 620 CSS px, integral at DPR 1/2/3; `toFixed(1)` bounds the seam to ≤ 0.1 px; measured pixel-identical before the seam and 41 dB after it (invisible). Expected: Safari p50 26 → 17, p95 50 → 22 (F2/F3); Chromium +8–16 fps (labrat).
   - Reserve: CSS scroll-driven animation for this layer (Safari 26+, acceleration on 26.6.2 unverified, NO-LIST §E allows it only decorative-behind-`@supports`): not this round.
**P1.2 Wake without a stale frame (F9).** In the scroll path of `wake()` (:8372–8379), when the engine is stopped (`!running`), `booted`, and not RM, run `work(scrollY)` synchronously once before scheduling the frame, then set `lastY = y`. **[r2] Traps:** distinguish the scroll Event (currently arriving as `force`) from `wake(true)` (resize) and the IO wake (:8391); never sync while `running` (the approval carry's per-frame `scrollTo` at :8980 runs while `departing` holds the engine open, so wake early-returns — no reentrancy); the claim is "the content process no longer presents a frame with stale rail/figures", not "the async scroll lead is gone" (on iOS the compositor moves the page before the content process hears about it).
**P1.3 `--scrim-c` written on `#mast`, not `<html>` (F6).** Only `#mast::before` reads it. Zero visual change; removes a full-document style resolve per colour step on every WebKit device; matters most with the morning's DOM in the tree.
**P1.4 [r2, demoted to hygiene] Wash memoised.** `drawWash` skips a draw only when all five inputs are bit-identical to the last draw. No quantisation (visible stepping risk during slow scroll, unmeasured). Claimed gain: ~0; it costs nothing and stops redundant GL work while the page is still but the engine runs.
~~P1.5~~ **[r2, dropped]**: the fx loop already skips non-near elements (:8334); it costs 0.03 ms/frame (F10).

Verification P1 (commit gates): real-Safari keyboard batch base vs P1 build **including `contour-short` specifically** (F2 tested *hidden*, not *short*) + the owner's manual scroll at his seat; labrat matrix on webkit/chromium/firefox headless at 1440×900 **and** 1512×1500 (the guard's static branch); wrap-straddle screenshot diffs at DPR 1/2/3 and page zoom 50/200% with a ≥ 6 s settle (the nameplate's control lands at ~4.1 s); full `verify:portfolio` (gates + hash) on macOS and in the Linux container; rebaseline in its own commit.

## 3. Phase 2 — mobile (iOS Safari first, then Android Chrome), small diffs  **[r2: moved before the morning; both complaints are about the main run]**

**P2.1 A stable viewport height (F7). [r2 rule from yoda C2]** Define `vh` as the `offsetHeight` of a fixed `height:100vh; width:100vw` probe element: that *is* the large viewport (`lvh`, iOS 15.4+), which every CSS-sized section already uses (:399 etc.), so JS and CSS agree for the first time. On any `resize`: if the probe's height **and [r3] the probe's `offsetWidth` (= `lvw`, so an iOS pinch-zoom, which changes `innerWidth` but not the layout viewport, does not count)** are unchanged, it is a toolbar / visual-viewport transition → **all four listeners skip** (engine :8396, wash :4432, dawnscape :11796, flock :13245); otherwise the existing full path runs. No threshold, no touch-sniffing, desktop window drags unaffected by construction. Exceptions kept dynamic: the approval carry's scroll target (:8968) needs the *reachable* max scroll (`docH − current innerHeight`); `washSeat` (:8159) keeps reading `innerWidth/innerHeight` (it positions the glow in the live viewport). Halt tolerance: `yEnd = docH − lvh`; toolbar-collapsed max scroll equals it exactly, toolbar-expanded overshoots and every consumer clamps (:8253/8256) — labrat re-proves the 390×844 ring-draw check (:8258–8265) under the new definition on macOS and Linux.
**P2.2 Arrival pacing on `mobile` (F8): widen the windows.** Cards and headings get arrival windows spanning ~500 px of scroll on phones (`in .0 .45`-class instead of `in .1 .3`), chosen by picasso per element class so the drift and fade still read as one gesture. Stays "a pure function of scrollY" (:8246 "any jump lands right"); no time-smoothing (NO-LIST §E, no touch smoothing). Residual, stated: a peak flick (70 px/frame) still crosses 500 px in ~7 frames; that is the physics of pure-scrollY and accepted.
**P2.3 Contour static on iOS-family** (from P1.1's guard).
~~P2.4 Cheaper rail draw~~ **[r3, cut from this round]**: no real device measured `drawThread` as a cost (owner's iPhone `work()` 1 ms; `nothread` inside the noise band on desktop), and it touches the renderer under the "Mac rail never regresses" ruling and the whole G10 family. Folded into the Phase 4 decision.
**P2.5 [r2] `webglcontextlost` / `webglcontextrestored` handlers** on the wash (none today): on iOS a GPU-process kill would freeze the wash forever; on loss fall back to the `no-gl` sun, on restore re-create the program and re-draw.
**P2.6 The 60 Hz cap on ProMotion phones (F11)** cannot be lifted; P1.2 and P2.1 make what the page draws coincide with the first scrolled frame, which is the part a reader notices. The structural answer (the rail living in the document and scrolling at 120 Hz natively) is **Phase 4**, the owner's decision after Phases 1–3 are measured.

Verification P2: **[r3] first a device log** — the harness recorder now logs `(probe offsetHeight, probe offsetWidth, innerWidth, innerHeight, visualViewport)` on every `resize` so one iPhone session with scroll, pinch and rotate confirms the probe rule before it is coded; then the owner's iPhone session (toolbar transitions must show zero rebuilds: the harness logs `innerHeight` and DOM mutations per frame), iOS 26.5 + 18.3 simulators, labrat phone emulation (iPhone 14/15 Pro), the halt-tolerance proof, **and the full `verify:portfolio`** (desktop G10/G10b/c/d included, since `vh` feeds the rail), then Chrome/Firefox desktop for no regression.

## 4. Phase 3 — ¶13 the morning (F5), one designed round by picasso

**P3.1 Give the dawnscape its own compositing layer** (`will-change: transform` on `.dawnscape`), so scrolling no longer repaints the 750-path drawing.
**P3.2 Take the live creatures out of the static drawing, as overlays inside `.dawnscape`. [r2]** Everything that animates after the morning arrives (chicks, deer, gulls, butterflies, daisies in the wind, rays, pool reflection) moves into small overlay `<svg>`s positioned over the landscape *inside the `.dawnscape` container*, each its own layer, animating transform/opacity only; the landscape SVG becomes static once built (its only remaining change: the token flip, once). Rasterising the landscape is **rejected**: `check-dawnscape` requires the drawing present with its paths (check 3), counts live CSS animations inside `.dawnscape` (check 2) and reads stroke tokens on elements (check 4), and the r14/r15 rulings ("the morning notices the pointer", "a creature must look before it hops") need live, JS-driven creatures. Check 8 (a moving mask ≤ 2× its group) constrains how overlays are composed. **P3.1 alone does not meet the idle target** (F5: animations-off alone = no help; composited + silent = 18/17): the split is the fix.
**P3.3 Pause the morning's animations when ¶13 is off screen** (IntersectionObserver on `.bdawn` → `animation-play-state: paused` / WAAPI `pause()`), so the page costs nothing after the reader leaves the morning.
   - Design authority: picasso. Gates: `check-dawnscape` (16 seats, arc rule, chick checks, registry checks 4/9–12) must pass on the split DOM or be updated in the same commit with its negative probes re-proved red first.
   - Fallback if P3.2 balloons: P3.1 + P3.3 ship first; the idle cost then returns only while creatures move and the reader is in ¶13.
   - Dependency: P2.1 first, or re-measure ¶13 on the phone knowing the toolbar rebuild storm (dawnscape + flock listeners) is still live.

Verification P3: real-Safari `approve` batch (needs a 2-minute screen window) + headless `approve` series (base vs P3), idle and moving frames in beat 12; `check-dawnscape`; labrat matrix; the morning's r14/r15 behaviours re-checked in the ending-sequence tests (b, b2, c2, daisy resize).

- P2.1 changes the meaning of `vh` in one place that beats, fx, the rail, the dusk chain and the halt tolerance read; labrat's phone matrix and G10 at 390/430 must stay green on macOS and Linux.
- P3.2 is the largest diff; its fallback is stated.
- If the owner updates to Safari 27 mid-round, the desktop baseline is re-recorded before judging Phase 1 (27 changes a canvas-compositing behaviour).
- [r3] Residual unmeasured: whether a macOS pinch (`pageScaleFactor`) multiplies into the tiling test; failure mode is today's jank, not breakage. A 2-minute Web Inspector Layers-panel look at the P1 build on the owner's Safari would be the one direct observation of the mechanism; optional.
